## 二、偏差分析

预估合计 630 分钟，实际 705 分钟，超出约 **12%**。主要偏差在这几处：

| 环节 | 偏差 | 原因 |
| --- | ---: | --- |
| 需求分析 +70 | 超 | 作业原文没有规定「重复率」到底怎么算。花了额外时间试了 LCS÷原文长度、LCS÷抄袭版长度、`1 - 编辑距离/原文长度` 等好几种口径，并在样例上逐一比对 |
| 具体编码 +20 | 超 | 位并行 LCS 的进位/借位可以合并成一次比较，这个写法调了几轮才写对，靠的是和动态规划版本做差分测试才敢确认 |
| Code Review +5 | 略超 | 严格编译警告（`-Wconversion` 等）和 cppcheck 各报了一批问题，逐个改掉花了时间 |
| 测试 +15 | 超 | 环境本身有坑：MinGW 的 gcov 写不出含中文路径的 `.gcda`；gprof 在 Windows 上采不到样。为了拿到覆盖率与性能数据额外折腾了一段时间 |
| 设计复审 −5 | 略省 | 模块划分（common / fileio / check / main）一次就定下来了，没有返工 |

## 三、事后总结与过程改进

**做得好的地方：**

1. **先把「输入输出边界」和「纯计算」拆开**。`check.c` 里全是
   「长度进、长度出」的纯函数，一个字节的文件都不碰，所以单元测试极好写，
   覆盖率也上得去（`check.c` 行覆盖 93.98%）。
2. **用差分测试保证优化的正确性**。位并行 LCS 这种满是位运算的代码，
   光靠人眼看是看不出来的。写了「随机 2000 组串，两套算法结果必须相同」
   的用例，才敢把生产代码换成新算法。
3. **性能问题用数据说话**。先用 gprof 确认 100% 的时间都在 `check_lcs_dp` 上，
   再动手优化；优化完再采一次样，确认瓶颈真的消失了，而不是凭感觉猜。

**下次要改进的地方：**

1. **需求不明确时要更早停下来确认**。「重复率怎么定义」这个问题我拖到写代码
   之后才意识到，如果一开始就画个流程图把输入输出的语义钉死，能省下不少返工。
   （PSP 里「需求分析」超了 10 分钟，就是这个原因。）
2. **别在工具链上耗太久**。中文路径导致 gcov 失效这种事，正确的做法是
   第一时间把工程放到纯 ASCII 路径下，而不是反复试。
3. **预估要拆得更细**。「具体编码 180 分钟」这种粒度的预估几乎没有约束力，
   应该按「字符统计模块 / LCS 模块 / 命令行模块 / 错误处理」分别估。
