# 性能分析说明

本目录记录第三次作业的性能测量方法、原始数据与结论。

- `perf-analysis.svg`　性能分析图（博客"效能分析"一节引用）
- `bench-output.txt`　基准程序的实际输出

## 一、怎么测的

程序本身会打印生成与判题的耗时，但要做**归因**（时间到底花在哪个函数上）还不够，
因此额外写了一个临时基准程序：它排除 `Program.cs`（避免与 `Main` 冲突），
与 `src/` 下的源码一起编译，直接调用各层的公开接口分段计时。

```bash
# 在 src 目录下，把基准程序与源码一起编译（Bench.cs 不随仓库提供，仅用于测量）
csc -nologo -codepage:65001 -target:exe -optimize+ -r:System.Numerics.dll \
    -out:bench.exe Fraction.cs Expression.cs ExpressionParser.cs ProblemGenerator.cs Grader.cs Bench.cs
```

测量时注意了两点：

1. **预热**：先跑 200 道题让 JIT 完成编译，避免把首次运行的开销算进去；
2. **多次取最小**：每项测 5 次取最小值，而不是取平均，以压低机器噪声带来的偏差。

测量对象：`-n 10000 -r 10`。

## 二、原始数据

| 阶段 | 耗时 |
| --- | --- |
| 生成 10000 道题（端到端，含查重） | 68.93 ms |
| ├ 构造题面 / 答案 / 规范串 | 15.11 ms |
| │　├ `ToInfix` 题面渲染 | 8.84 ms |
| │　└ `ToCanonical` 查重键 | 6.02 ms |
| ├ 查重：`HashSet`（本项目采用） | 1.55 ms |
| └ 查重：`List` 线性查找（朴素做法） | 589.91 ms |
| 写出 Exercises.txt + Answers.txt | 4.68 ms |
| 判题 10000 道（端到端） | 30.74 ms |
| └ 其中解析表达式并求值 | 18.02 ms |

## 三、结论

1. **查重结构是唯一的"生死选择"**。同样是对 10000 个规范串去重，`HashSet` 只要 1.55 ms，
   而 `List<string>.Contains` 线性查找要 589.91 ms（慢 380 倍，超过整个生成流程的 8 倍）。
   原因是后者要做 `n(n-1)/2 ≈ 5000 万次`字符串比较。**这个性能差距在设计阶段就决定了**，
   不是靠事后调优能补回来的。
2. **单个函数里开销最大的是 `Expression.ToInfix`**（题面渲染，8.84 ms / 10000 次 = 0.88 μs/次），
   其次是 `Expression.ToCanonical`（6.02 ms，0.60 μs/次）。两者合计 15.11 ms，
   占生成阶段的 22%，这部分是"必须生成字符串"的固有成本。
3. **生成阶段剩下的约 52 ms（76%）是表达式树的随机构建与候选筛选**
   （递归建树、随机取值、丢弃"太水"的候选后重试）。这是残差推算：68.93 − 15.11 − 1.55 = 52.3 ms。
   按概率估算重试率约 2%~3%，即 10000 道题大约只多建了几百棵树，因此这部分基本是算法本身的必需开销。
4. **判题的 30.74 ms 里有 18.02 ms（59%）花在解析表达式并求值上**，其余是读文件、比对与写报告。

## 四、已实施的优化

| # | 措施 | 效果 |
| --- | --- | --- |
| 1 | 查重使用 `HashSet<string>` 而非 `List` | 1.55 ms vs 589.91 ms，快 380 倍 |
| 2 | 规范串在 `Problem` 构造时算好并复用（`Contains` 与 `Add` 用同一个字符串） | 省下约 6 ms 的重复计算 |
| 3 | 子表达式的值在构造节点时算好并缓存 | 约束检查、答案计算、判题比对都直接读缓存，不重复递归求值 |
| 4 | `MakeNode` 用"交换左右"代替"整道题重来" | 重试率降到 2%~3% |
| 5 | 写文件先拼成一个大字符串再落盘 | 10000 行只需 2 次文件写入，共 4.68 ms |

## 五、考虑过但主动放弃的优化

**把查重判定提前到构造 `Problem` 之前**：先算规范串、判重，通过了再去构造题面字符串，
这样被丢弃的候选就省下了题面渲染的开销。

放弃的理由：实测重复率低于 2%，能省下的约是 `8.84 ms × 2% ≈ 0.18 ms`，
而代价是把"构造一道题"的逻辑拆成两处、可读性下降。**收益远小于引入的复杂度。**

这条比前五条更值得记下来：优化的前提是测量，不是直觉。
